# Security boundaries

The bridge binds only to IPv4 `127.0.0.1`. HTTP and WebSocket requests require the expected Host; browser HTTP requests require the matching Origin. No permissive CORS headers are sent. Native controls require a random bearer token in a WebSocket header and reject browser Origin headers. The overlay has a separate read-only token, requires the local Origin, receives only events and overlay display settings, and is disconnected if it sends commands. Credentials and account control state are never sent to it.

Overlay URLs include a fragment capability so the initial HTTP request does not send it to the server; JavaScript removes the fragment from the page URL before connecting. The event socket sends that capability in its query string. Request logging is disabled. Treat the full URL as private. Capabilities rotate on bridge restart. A malicious process running as the same Windows user remains outside this protection boundary; it can inspect environment/process memory or use that user's DPAPI.

OAuth uses a separate ephemeral loopback server, five-minute single-use state, and PKCE S256. Refresh/access credentials are serialized only to DPAPI ciphertext using a fixed PowerShell program and stdin. They are never passed as shell arguments or logged. Native QSettings stores public desktop client configuration, not access/refresh tokens. The desktop client secret is a public installed-app parameter, stored locally in QSettings; do not put privileged server credentials there.

Input is validated with Zod. Request size, WebSocket payloads, client count, command rate, send rate, deduplication sets, spam buckets, history and output backpressure are bounded. Native rich text escapes message/author text; only generated image markup can load a validated media URL. The native media cache fetches approved HTTPS platform CDNs without cookies/redirects and enforces queue, byte, pixel and cache limits. Overlay text uses textContent and DOM-created images. Overlay content uses a restrictive CSP. No arbitrary program paths or shell commands are accepted over the bridge; Node/package paths are selected locally by the user in the native Settings UI.

Windows Job Object ownership kills the bridge and its child processes when its handle closes. The bridge also checks its OBS parent and shuts down on stdin closure or a shutdown command. During normal teardown, the native plugin requests shutdown then force-kills after a bounded wait. This lifecycle source still requires validation in an actual OBS build.
